1. What we're building
Map Pin is a new question type for classroom geography-style quizzes:

The question: the projector shows a prompt ("Where is Denver?"). Each phone shows an image on a canvas. The player taps to place a pin, adjusts it, then presses Confirm. Nothing submits automatically when time runs out.
Scoring:
The target is stored as an (x, y) position measured as a fraction (0–1) of the image's width and height.
Distance is corrected for the image's shape, so it's measured in "image-width units". That keeps the scoring circle round on a non-square image.
A tap inside fullRadius gets full points and counts as correct. Credit falls off in a straight line to zero at zeroRadius.
COMPLETENESS mode gives full points for any valid tap.
Image storage: a new images table stores the bytes in the database.
Images can never be changed, and v1 has no delete.
Admins and course hosts can upload. On upload, images are rotated upright, re-encoded to remove metadata (keeping the colour profile), and capped at 2 MB.
Anyone logged in, including guests, can read an image by its random UUID. There's no endpoint that lists images.
Preloading: phones get the game's image IDs in sync_state.imageIds when they join, and again in a new game_images event at game start. They fetch the images with the Bearer token, keep them as blob URLs, and cache the load in progress so the same image is never fetched twice.
Host results: the map with a 50×50-grid heatmap of taps, the target, and both radius circles. Game-over shows the "within target" % and average credit.
Import/export: bundles move to version 2, which carries images as base64. Image IDs are remapped on import, and a bundle may only reference images it contains.
Fix that comes with it: a question edit (PUT) now re-validates the whole merged question, for every question type.
Also covered: editors in both admin and host, the HTML report, 12 integration tests, a sample game, and updates to the context docs.
That matches the decision list in the revision history.

2. Gaps, ambiguities and contradictions (worst first)
🔴 Blocking: fix before implementing
B1. The "has metadata?" rule (§4.3 step 4) contradicts itself, and either reading breaks something.

It first names a short list: EXIF, XMP, JPEG comment, PNG text chunks. Then it says "anything in Pillow's info other than icc_profile, dpi, transparency, gamma." Those two rules disagree.
Under the second rule: every JPEG Pillow saves gets a JFIF header. Pillow then reports jfif, jfif_version, jfif_unit and jfif_density in info (and sometimes progressive or adobe). So every Buzzer-exported JPEG counts as "has metadata" and is re-encoded on import. Byte-identical round trips break, and so does test 11.
Under the first rule: Photoshop/IPTC data (info['photoshop'], which can hold author and location) and MPF data are never caught. They would survive a hand-made import.
Fix: write an explicit per-format list of allowed info keys, and say what happens to everything outside it.
B2. COMPLETENESS reveals contradict each other.

§4.5 says that for COMPLETENESS, "if the target is present, it is revealed on the results screen."
§4.6 says COMPLETENESS returns {"type": "completeness"} before the map-pin reveal is ever built, so there's no image or target. §4.10 says the player shows only "Answer recorded".
map_pin_reveal has nullable target/radius fields, but nothing could ever produce a null.
§4.11 doesn't say what the host results page shows for a COMPLETENESS map-pin question. MapPinHeatmap needs an imageId, and that reveal doesn't have one.
Fix: choose one behaviour and write it into §4.5, §4.6, §4.10 and §4.11.
B3. resolve_map_pin_image on the import path can't work as written.

§4.5 says import calls it, and it raises IMAGE_NOT_FOUND when the image isn't in the database.
During import, the bundle's images aren't in the database yet. §4.8 step 3 instead takes the dimensions from the decoded bundle images.
Fix: either call it after the images are flushed and the IDs rewritten, or say import doesn't call it.
B4. Import has no function to call.

§4.8 says "keep the prepared output; don't decode twice." But store_image(db, raw, …) always runs prepare_image itself.
Fix: add something like store_prepared(db, prepared, user, course_id) to §4.3.
B5. Score storage type is never stated.

round(points_value * frac, 2) produces decimals like 7.35.
The spec never says whether points_awarded and leaderboard totals can hold decimals. If they're integers, this truncates silently or fails.
It also doesn't say whether map-pin gets any speed bonus that other types might have. "Existing per-question sum" isn't enough to tell.
🟠 High: an implementer would have to guess
H1. The Confirm-near-the-deadline race is ignored.

§3 rejects auto-submit because submitting after the lock sends an error, and an error ends the player's game view.
Pressing Confirm by hand in the last few hundred milliseconds hits exactly the same race. Place → adjust → confirm makes late submits more likely.
The spec needs to say how the player app handles a "question locked" error, so it doesn't end the game view.
H2. The canvas has no size rule on the phone.

"CSS-sized to its container" doesn't say what decides the container's height. Without that, a canvas defaults to 150px tall or collapses.
Fix: state a rule, for example full width, with height = width ÷ aspect, capped at about 60% of the viewport height.
H3. "Don't buffer a huge upload" (§4.4) isn't true in FastAPI.

Starlette reads the whole multipart body into a spooled temp file before the handler runs, so reading 2 MB + 1 byte inside the handler doesn't prevent buffering.
A real limit has to come from the server or proxy, or from checking Content-Length and the stream before parsing. The same applies to "reject files over 25 MB before reading" on import.
H4. Two errors are mislabelled in the decompression guard and test 2.

Pillow's limit: Image.MAX_IMAGE_PIXELS raises DecompressionBombError only above 2× the limit. Between 40M and 80M pixels it just warns, and the image still decodes. The 8000×8000 cap (64M) is also above 40M.
Global setting: it's a module-level global, not a per-call setting.
Check order: dimensions should be checked (after Image.open, before load()) so oversized images never decode.
SVG: Pillow can't open SVG at all, so SVG fails at step 2 with 422 INVALID_IMAGE, never reaching step 3's 415. Test 2's "415 / 422" should say which input gets which code.
H5. Expired guest tokens on the player app.

loadImage uses "the app's existing api auth handling". But §4.9 also says the player's api.ts is an older wrapper that loadImage shouldn't change.
If a guest's access token expires mid-game, the image fetch returns 401 and every retry does too.
Fix: say whether the player blob fetch refreshes the token, or confirm that guest tokens outlive a game.
H6. The update-path merge (§4.5) leaves three things unclear.

QuestionCreate may require fields the merged object doesn't include (game_id, order_index?).
"Non-null fields" means a PUT can never deliberately clear a nullable field.
Validation now runs before prompt sanitizing. The spec should confirm that matches create, or rule it out.
🟡 Medium
M1. WebP "lossless if the source was lossless": Pillow has no standard flag for this. The spec should say how to detect it (for example, look for a VP8L chunk).
M2. Hand-made bundle IDs: they can be any string (§4.8), but QuestionCreate requires imageId to look like a UUID. So a hand-made bundle using "map1" fails. Either loosen that check during import or state that bundle IDs must be UUIDs.
M3. Unused bundle images: all of them are validated, but only referenced ones are stored. A bad unused image still fails the whole import. Say whether that's intended.
M4. Host summary edge cases:
withinFullPct is "share of answers", which leaves several things open: percent or 0–1, what happens with zero answers (divide by zero), and whether the denominator is answers or players.
Under COMPLETENESS, it would show 100% if is_correct is always true.
M5. Player results labels:
A player who didn't answer gets "Too far" under the points-based rule. They need a "No answer" state.
With points_value == 0, the labels can't be told apart. Using is_correct plus points > 0 would be cleaner.
The pin comes "from local state", so it's lost on a page reload.
M6. Host refresh mid-game: the host never gets imageIds in sync_state, so a refreshed projector has to load on demand. That's probably fine, but it isn't stated.
M7. The MEDIUMBLOB column comes from the MySQL dialect, which breaks any test that runs on SQLite. Use LargeBinary().with_variant(MEDIUMBLOB, "mysql"), or confirm tests only run on MySQL.
M8. Editor vs. server on missing images: the editor blocks saving only ACCURACY questions without an image. But the server requires config.imageId for both grading types, so a COMPLETENESS question without an image gets a server 422 instead of a form error.
🟢 Low
Name clash: the Image model collides with PIL.Image in image_service. Say which import alias to use.
Imported radii vs. editor sliders: sliders cover 0.02–0.5, but the server allows zeroRadius up to 2. An imported question with a large radius gets silently clamped when opened in the editor and saved.
Width/height values on input: imageWidth/imageHeight are "optional on input", but their type isn't validated ("abc" is accepted, then overwritten).
Drag into the letterbox: taps in the empty bars are ignored, but the spec doesn't say what a drag into them does (clamp or ignore).
Test 8 and NaN: {x: NaN} "sent as a string or null" is also missing y, so it never tests NaN. Python's json.loads accepts a literal NaN, so add a raw-NaN case.
Animated images: how to detect them isn't stated (getattr(img, "is_animated", False)).
Report SVG: reusing one embedded image across several SVGs needs <use href="#id"> or a shared <defs>. The spec could say so.
Admin upload error: the code for a bad course_id ("404 if given and missing") isn't named.
Rate limiter: the slowapi decorator needs a request: Request parameter in the handler.
Questions created outside the service: scoring divides by imageWidth/imageHeight, but calculate_score is only defensive about x/y. A question created without dimensions (seed scripts, direct inserts in tests) would crash it.
