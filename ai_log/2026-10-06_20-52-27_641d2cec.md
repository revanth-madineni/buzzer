## Repo and Codebase Organization

The broad flow of code goes from index.html -> Main.ts -> GameManager.ts -> Everything else. Index.html is the entry point. It exists outside of src and defines the globals p5.js uses to run. Those globals are values that exist in Main.ts. Main.ts is exclusively used to store functions for p5.js. Main.ts breathes life into the state manager, GameManager.ts. GameManager handles the functionality of draw() and update() across numerous states, like Running, Menu, Loading, Finished, etc. It also processes gameActions tied to inputs that are recorded by the InputManager.

All 'living' entities are considered sprites. Creature inherits from sprites to add the NORMAL/DYING/DEAD states, and the player is an offspring of creature. The specific ufo/fly and grub/weird floor monster classes are defined within the creature file itself. You may notice this differs from how meteor is handled. Meteor is a direct offspring of sprite, yet it is not at the bottom of sprite's file, like the grub is for creature.ts. I prefer this method of organization, but the grub/fly were already baked into the creature.ts from the template, and since we are working in an 'old' codebase, less changes = better to avoid confusing existing engineers (hypothetically speaking, of course). 

GameManager also updates the GameMap, from GameMap.ts. The GameMap handles, of course, the game map, as defined in easy to visualize .txt files that are later parsed into entities and map objects.

Assets (map text files, images, sounds, and spritesheet settings (resources)) are in the assets folder. These are loaded into 'loads' by ResourceManager during the loading state of the game (the spritesheets contained here are also sliced into frames at this step).

Settings is the 'm' menu. It is layered over the top of the game, and allows for minor setting adjustments.

SoundManager is called by GameMap and Settings, and handles playing the sounds loaded into ResourceManager. It owns the toggles too, so the 'm' menu and the B/S hotkeys don't disagree.

Tests, unsurprisingly, live in /tests and are run with vitest. They are named after the file they cover.

Build contains the compiled build (gitignored)

Flow of a frame:
- Main.ts draw()'s, clearing the canvas, determining the scaleFactor, and running GameManager's .update() (if the window is focused)
- GameManager.ts update()'s, checking the game state and acting accordingly. When running, it calls map.update() to move the world.
- GameMap.update then handles updating countdown timers (and spawns a meteor for the end of a meteor countdown), updates the score to their furthest tile, moves the player with updateSprite() (handling gravity, collisions, sprite 'stomping', and powerup pickups as well (acquirePowerUp())), It then advances the animation clock for the player sprite, and then loops through and updates every other sprite's state, position, and animation (if applicable) (ex. removes dead enemies, animates pickups, etc).
- InputManager's checkInput is then called by GameManager to read the keyboard
- GameManager then calls processActions to turn those inputs into real changes. After, it checks the result. If the player is dead, it switches the state to finished, if it finds map.won, then it switches the state to Won (etc). The player speed is calculated in the processActions step (and then used in the next map update to move the player)
- GameManager, now having updated states, draws it with draw(). If the game is running, the GameMap is "drawn". If we are in the Menu, the html menu is also drawn (etc)
- GameMap.draw(), for example, computes the player's offset, handles the parallax backgrounds, adds a jump flame under the player if airborne, and other visual updates.
- Main.ts then adds white rectangles to cut off the game on the sides, and p5 then shows it on the browser
